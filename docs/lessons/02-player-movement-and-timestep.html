Lesson 02: Player Input, Vectors, FixedUpdate & Wall Physics

Now that you have a bounded 2D arena, let's spawn the player's square and give it smooth, physically grounded movement at 1.2× base speed—avoiding the three classic beginner game-physics bugs: diagonal speed-boosting, frame-rate-dependent speed, and sticky walls.

1. Vector Normalization: Fixing the 41% Diagonal Speed Exploit

When reading 8-directional keyboard input, you start with let mut dir = Vec2::ZERO; and add +1.0 or -1.0 on X and Y for each held key. If the player holds D alone, dir = (1.0, 0.0), which has length 1.0. What happens when they hold W + D simultaneously?

By the Pythagorean theorem, dir = (1.0, 1.0) has length √(1² + 1²) = √2 ≈ 1.4142! Without normalization, moving diagonally multiplies the player's speed by 1.414×. Dividing a vector by its length projects it back onto the unit circle (length 1.0): 

// Safe even when dir == Vec2::ZERO (no division-by-zero NaN!)
let unit_dir = dir.normalize_or_zero();

2. Why Physics Belongs in FixedUpdate + Velocity Steering

Bevy has two primary per-frame schedules:

  • Update runs once per rendered frame (e.g., 60 Hz on a laptop, 144 Hz on a gaming monitor, or 15 Hz during a lag spike). Great for UI and camera polish, dangerous for collision physics: a large variable dt can let a fast square teleport through another square in a single frame ("tunneling").
  • FixedUpdate runs at a deterministic fixed frequency—64 Hz by default in Bevy (dt = 1/64 s = 0.015625 s). If a frame takes longer, Bevy steps FixedUpdate twice to catch up; if rendering runs at 240 Hz, FixedUpdate only steps when 15.625 ms of simulation time has accumulated. Even better: inside any FixedUpdate system, Res<Time> automatically provides that fixed timestep!
Physics Design Choice: Smooth Velocity Steering vs. Hard Overwrite

In Lesson 03, colliding squares will bounce off one another by adding an impulse to Velocity. If your input system sets velocity.0 = desired_velocity directly, it erases 100% of any knockback impulse 15 milliseconds later! Instead, blending current velocity toward desired velocity using linear interpolation—velocity.0 = velocity.0.lerp(desired, (PLAYER_ACCEL * dt).min(1.0)) with a snappy rate like PLAYER_ACCEL = 18.0—gives responsive arcade controls and lets physical collisions push squares cleanly!

Wall Sliding Math

Suppose the arena has half_size = (400, 280) and your player square is 28 × 28 (collider.half_size = (14, 14)). The player's center can never exceed limit = arena.half_size - collider.half_size = (386, 266). When pos.y > limit.y:

  1. Clamp position: pos.y = limit.y.
  2. Zero outward velocity only: if vel.y > 0.0 { vel.y = 0.0; }. Notice we leave vel.x untouched—so holding W + D against the top wall lets you slide smoothly along the wall to the right!

pub const BASE_SPEED: f32 = 220.0;

pub struct Character;

pub struct Player;

pub struct Velocity(pub Vec2);

}
Rust Concepts Inside This Snippet:
  • The Newtype Pattern (Velocity(pub Vec2)): Why wrap Vec2 in Velocity instead of attaching a raw Vec2 as a component? First, Rust's orphan rule forbids deriving external traits on types you don't own. Second, if an entity ever needed both velocity and acceleration, two raw Vec2 components would collide—distinct wrapper types give type-safe meaning!
  • #[derive(Deref, DerefMut)]: Re-exported in bevy::prelude::*, this implements std::ops::Deref<Target = Vec2>, allowing you to call Vec2 methods like vel.extend(0.0) directly or access the inner field explicitly via vel.0.

fn spawn_player(mut commands: Commands) {
    commands.spawn((
        Character,
        Player,
        Sprite::from_color(Color::srgb(0.30, 0.67, 0.97), Vec2::splat(CHARACTER_SIZE)),
        Transform::from_xyz(0.0, 0.0, 2.0),

Rust Concepts Inside This Snippet:
  • Vec2::splat(v) is a handy constructor shorthand for Vec2::new(v, v)—ideal for squares!
  • Velocity::default() calls the derived Default trait implementation, producing Velocity(Vec2::ZERO).
Step 3

Write the Three FixedUpdate Physics Systems

Implement three focused, single-responsibility systems and register them in FixedUpdate using .chain():

  1. player_input: Reads Res<ButtonInput<KeyCode>> and Res<Time>, queries (&MoveSpeed, &mut Velocity), With<Player>, builds a Vec2 from WASD / Arrow keys, calls .normalize_or_zero(), multiplies by speed.0, and smoothly blends vel.0 = vel.0.lerp(desired, (PLAYER_ACCEL * time.delta_secs()).min(1.0)).
  2. apply_velocity: Reads Res<Time>, queries (&Velocity, &mut Transform), and integrates transform.translation += velocity.0.extend(0.0) * time.delta_secs().
  3. confine_to_arena: Reads Res<ArenaBounds>, queries (&mut Transform, &mut Velocity, &Collider), computes limit = arena.half_size - collider.half_size, clamps x and y to [-limit, +limit], and zeroes outward velocity when touching a wall.
Step 3 Reference Solution 
fn player_input(
    keyboard: Res<ButtonInput<KeyCode>>,
    time: Res<Time>,
    mut query: Query<(&MoveSpeed, &mut Velocity), With<Player>>,
) {
    let mut dir = Vec2::ZERO;
    if keyboard.pressed(KeyCode::KeyW) || keyboard.pressed(KeyCode::ArrowUp) {
        dir.y += 1.0;
    }
    if keyboard.pressed(KeyCode::KeyS) || keyboard.pressed(KeyCode::ArrowDown) {
        dir.y -= 1.0;
    }
    if keyboard.pressed(KeyCode::KeyD) || keyboard.pressed(KeyCode::ArrowRight) {
        dir.x += 1.0;
    }
    if keyboard.pressed(KeyCode::KeyA) || keyboard.pressed(KeyCode::ArrowLeft) {
        dir.x -= 1.0;
    }

    let unit_dir = dir.normalize_or_zero();
    let blend = (PLAYER_ACCEL * time.delta_secs()).min(1.0);

    for (speed, mut velocity) in &mut query {
        let desired = unit_dir * speed.0;
        velocity.0 = velocity.0.lerp(desired, blend);
    }
}

fn apply_velocity(time: Res<Time>, mut query: Query<(&Velocity, &mut Transform)>) {
    let dt = time.delta_secs();
    for (velocity, mut transform) in &mut query {
        transform.translation += velocity.0.extend(0.0) * dt;
    }
}

fn confine_to_arena(
    arena: Res<ArenaBounds>,
    mut query: Query<(&mut Transform, &mut Velocity, &Collider)>,
) {
    for (mut transform, mut velocity, collider) in &mut query {
        let limit = arena.half_size - collider.half_size;

        if transform.translation.x > limit.x {
            transform.translation.x = limit.x;
            if velocity.0.x > 0.0 {
                velocity.0.x = 0.0;
            }
        } else if transform.translation.x < -limit.x {
            transform.translation.x = -limit.x;
            if velocity.0.x < 0.0 {
                velocity.0.x = 0.0;
            }
        }

        if transform.translation.y > limit.y {
            transform.translation.y = limit.y;
            if velocity.0.y > 0.0 {
                velocity.0.y = 0.0;
            }
        } else if transform.translation.y < -limit.y {
            transform.translation.y = -limit.y;
            if velocity.0.y < 0.0 {
                velocity.0.y = 0.0;
            }
        }
    }
}

And in main(), add spawn_player to Startup and chain the physics systems in FixedUpdate:

        .add_systems(Startup, (setup_camera, spawn_arena, spawn_player))
        .add_systems(
            FixedUpdate,
            (player_input, apply_velocity, confine_to_arena).chain(),
        )
Rust & Bevy Concepts Inside This Snippet:
  • &MoveSpeed vs &mut Velocity: Rust enforces explicit mutability down to each queried component! Asking for &MoveSpeed (immutable reference) documents that player_input never alters base speed, while &mut Velocity grants exclusive write access.
  • Query Filter With<Player>: Notice With<Player> is the second type parameter of Query<Data, Filter>. It filters matching entities without bothering to fetch the 0-byte Player struct into your loop tuple!
  • Why .chain() Matters: By default, Bevy runs systems in parallel when possible. Chaining guarantees input → integrate position → clamp walls happens in exact order every physics tick, so you never render a frame with the square halfway inside a wall!
